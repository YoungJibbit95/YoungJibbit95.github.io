# Konzept für das Portfolio von YoungJibbit95

Das Portfolio stellt YoungJibbit95 als unabhängigen Entwickler und als Person vor. Es verbindet die visuelle Sprache der Nexus-Produktseite mit einer persönlichen Geschichte: Aus Neugier entstehen Systeme, aus Experimenten zunehmend zusammenhängende Software. Die erste Version soll auf GitHub Pages laufen und deutschsprachig sein. Texte und Struktur werden so angelegt, dass Englisch später ergänzt werden kann.

Die gestalterische Leitidee lautet **Aus Neugier wird Software.** Ein gemeinsames Netz aus Punkten, Bahnen und Verbindungen begleitet die Seite. Seine Form verändert sich mit dem Inhalt: Projektkonstellation, Architektur, nachvollziehbarer Planungsablauf und schließlich eine organische Landschaft. Animationen zeigen Beziehungen und Entscheidungen.

## Identität und Ton

Der sichtbare Name ist **YoungJibbit95**. Die Selbstbeschreibung aus dem GitHub-Profil bildet die Grundlage: unabhängiger Entwickler, Lernen durch reale Projekte, Interesse an der Verbindung von Gestaltung und Engineering. Verständliche Architektur, überprüfbares Verhalten, bewusste Grenzen und dokumentierte Entscheidungen sind wiederkehrende Themen. [GitHub-Profil](https://github.com/YoungJibbit95)

Die Texte sind direkt, persönlich und neugierig. Entwicklungsstände werden konkret beschrieben. Lernprojekte bleiben als solche erkennbar. Technische Begriffe erscheinen dort, wo sie etwas erklären; eine kurze verständliche Einführung steht jeweils davor.

Die vom Nutzer genannten Eigenschaften prägen den persönlichen Teil: wissbegierig, denkt gern in Systemen, findet gern Fehler und arbeitet lösungsorientiert. Musik, Cannabisanbau, Gaming, Natur und der Wunsch nach Weltfrieden gehören ebenfalls zu seiner Darstellung.

Ein besonderer Gedanke erhält Raum: Computer und Internet sind sein Hauptinteressenbereich geworden, obwohl er sie persönlich am liebsten wieder abschaffen würde. Diese Spannung soll als eigene Haltung lesbar sein, ohne eine glatte Selbstdarstellung daraus zu machen.

## Aufbau der Website

### Einstieg

Empfohlene Komposition: links Name, große Headline und kurze persönliche Einordnung; rechts eine räumliche Konstellation aus Projekten. Besucher erkennen unmittelbar, wer hier baut und was sie entdecken können.

Textentwurf:

> **Aus Neugier wird Software.**
>
> Ich bin YoungJibbit95. Ich denke gern in Systemen, finde gern Fehler und lerne, indem ich eigene Software baue – von verbundenen Workspaces bis zu Engines und nachvollziehbarer Planung.

Hauptaktionen: **Projekte entdecken** und **Über mich**. GitHub bleibt in der Navigation direkt erreichbar. Die Konstellation ist zugleich eine alternative Projektauswahl. Auswahl per Klick, Tastatur oder Touch zeigt einen kurzen Teaser und hebt passende Verbindungen hervor.

Die erste Bewegung dauert ungefähr eine Sekunde: einzelne Punkte ordnen sich, die Verbindungslinien entstehen, die Headline wird sichtbar. Danach bleibt die Szene ruhig. Beim Weiterblättern wird aus der Übersicht die erste Projektgeschichte. Eine alternative zentrale Hero-Komposition wird zum Vergleich gezeigt.

### Nexus als zentrale Fallstudie

Headline: **Eine Idee. Ein verbundenes System.**

Nexus wird als langfristiges Hauptprojekt beschrieben. Die öffentlichen Clients Nexus Main, Nexus Mobile, Nexus Code und Nexus Code Mobile teilen einen Runtime-Kern. Lokale Notizen, Aufgaben, Dateien und Entwicklungsabläufe bilden die inhaltliche Grundlage. Cloud-Funktionen werden ihrem tatsächlichen Entwicklungsstand entsprechend gekennzeichnet. [Nexus Ecosystem](https://github.com/YoungJibbit95/Nexus-Ecosystem)

Die Szene beginnt mit einer einzelnen Idee. Daraus werden Notiz, Aufgabe, Canvas und Code-Kontext. Anschließend öffnet sich die Darstellung: Vier Client-Flächen ordnen sich um **@nexus/core**. Ein Signal läuft durch die gemeinsame Verbindung und verdeutlicht die wiederverwendete Grundlage.

Der erklärende Text folgt drei Perspektiven: Warum ich Nexus baue; welche Gestaltungs- und Architekturentscheidungen mich beschäftigen; was ich dabei lerne. Echte aktuelle Produktaufnahmen geben den visuellen Bezug. Schwebende Labels benennen nur die gerade relevante Funktion. Ein Aufklappen der technischen Darstellung wird als animierter Übergang angeboten.

Ein eigener Link führt zur Produktwebsite, ein weiterer zum Repository. Historische Screenshots erhalten eine Versionsbeschriftung. Geplante Cloud-, Sync- oder KI-Funktionen werden nicht als verfügbare Funktionen dargestellt.

### Cerebri als nachvollziehbare Entscheidung

Headline: **Ein guter Plan muss erklärbar bleiben.**

Cerebri wird als deterministische Grundlage für zeitliche Planung in Rust vorgestellt. Die aktuelle Planung arbeitet mit begrenzter Suche für ein Zielobjekt und expliziten Fakten, Regeln und Grenzen. Gelernte oder neuronale Komponenten sind eine spätere Forschungsrichtung. [Nexus Cerebri](https://github.com/YoungJibbit95/Nexus-Cerebri)

Eine kleine illustrative Szene enthält eine Aufgabe, eine Deadline und bekannte Zeitblöcke. Kandidaten entstehen; ein Konflikt wird sichtbar; ein gültiger Vorschlag bleibt übrig. Besucher können eine Regel verändern und sehen, warum ein anderer Kandidat passt. Die Phasen **Vorschlag → Prüfung → Freigabe → Ausführung** bleiben getrennt. Ein Vorschlag überschreitet die Freigabegrenze erst nach einer bewussten Aktion.

Für die Portfolio-Version wird ein klar beschriftetes Beispiel gebaut. Eine echte Cerebri-Integration kann später über geprüfte, aus dem Projekt erzeugte Fixtures erfolgen. Die Szene darf keine Fähigkeiten behaupten, die der aktuelle Planer nicht besitzt.

Geplante Richtwerte: kurze Reaktionen etwa 150 bis 250 ms, Layoutübergänge etwa 450 bis 800 ms. Aufwendige Szenen starten erst bei Sichtbarkeit. Ein globaler Bewegungsregler bietet volle, reduzierte und ausgeschaltete Bewegung. Das System respektiert prefers-reduced-motion. Scrollen bleibt nativ; die Seite bleibt jederzeit direkt navigierbar.

Auf Desktop können ein oder zwei kurze feststehende Erklärszenen den Scrollfortschritt nutzen. Auf Mobilgeräten werden daraus gestapelte Szenen mit expliziten Schrittaktionen. Hover ergänzt Touch- und Tastaturbedienung. Jede wichtige Information ist auch als Text vorhanden.

## Technische Umsetzung

**React + TypeScript mit Vite** ist die gewählte Grundlage. React passt zum Nexus-Umfeld und zu den interaktiven Szenen. **GSAP mit ScrollTrigger** steuert zusammenhängende Übergänge und die wenigen Szenen mit Scrollfortschritt. SVG bildet Netze und Architektur ab; Canvas kann einen sparsam berechneten Sternenhintergrund übernehmen. Eine zusätzliche WebGL-Schicht wird nur für eine konkrete Szene mit erkennbarem Nutzen ergänzt. [GSAP ScrollTrigger](https://gsap.com/docs/v3/Plugins/ScrollTrigger/)

GitHub Pages veröffentlicht den statischen Build. Als persönliche Adresse ist **youngjibbit95.github.io** vorgesehen; dafür heißt das Repository **YoungJibbit95.github.io**. Ein normales Projekt-Repository kann alternativ unter einem Unterpfad veröffentlicht werden. Build und Bereitstellung werden über GitHub Actions eingerichtet. [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), [Vite auf GitHub Pages](https://vite.dev/guide/static-deploy.html#github-pages).

Die Startseite enthält die zusammenhängende Geschichte. Ausführliche Projektbeschreibungen können später echte statische Detailpfade erhalten. Basisinhalte werden für Suchmaschinen und Linkvorschauen vorgerendert. Projekttexte und Metadaten stehen in einer gepflegten zentralen Inhaltsstruktur. GitHub-Metadaten können beim Build eingelesen werden; die fertige Seite benötigt dafür keine laufende API-Abfrage.

Schriften und Bildmaterial werden lokal ausgeliefert. Szenen werden bei Bedarf geladen, unsichtbare Animationen pausiert und Partikelzahlen an Bildschirmgröße und Geräteleistung angepasst. Ein unabhängiger Dienst ist nur erforderlich, wenn später beispielsweise ein Kontaktformular Nachrichten versenden soll.
